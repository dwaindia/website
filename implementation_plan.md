# Unified Website Design, Sitemap, Technology & Phased Implementation Plan

## Google Antigravity --- Master Project Specification

**Organisation:** Dalit Welfare Association (DWA), Andhra Pradesh,
India\
**Project:** Official DWA Website\
**Design direction:** Original DWA editorial design inspired by the
design principles of Open Society Foundations\
**Technology direction:** HTML5, Tailwind CSS, Vanilla JavaScript,

# 1. Project brief and non-negotiable scope

Build a fast, accessible, mobile-first and institutionally credible
website for Dalit Welfare Association (DWA). The website must
communicate the organization's identity, history, purpose, programmes,
work, accountability and ways to support its cause.

The website must have **exactly five primary pages**:

1.  `index.html` --- Home
2.  `about.html` --- About
3.  `programs.html` --- Programs
4.  `accountability.html` --- Accountability
5.  `donate.html` --- Donate

All other information must be organized as sections, in-page tabular
navigation, anchor menus, accordions or structured content within these
five pages. Do not create additional top-level pages for Stories,
Projects, Events, Gallery, Impact, Governance, Contact or individual
programmes.

**Important scope rule:** The first development delivery is the Home
page (`index.html`) only. DWA must review and approve the Home page
before the other four pages are developed. Do not bypass this approval
gate.

The website should be a lightweight custom-coded platform, not a generic
SaaS dashboard and not a heavy plugin-dependent website.

### B. Donation amount selector and visual donation meter

Build an accessible, interactive donation amount selector with a visual
amount meter.

Recommended interaction:

-   Show a small set of editable suggested contribution amounts.
-   Include a custom amount field.
-   Display the selected amount clearly in Indian Rupees for domestic
    giving.
-   Provide a separate international giving route with the currency and
    payment instructions confirmed by DWA.
-   Update a visual progress meter or amount indicator when the visitor
    changes the selected amount.
-   Explain what the amount may support only when DWA has approved a
    current cost-to-impact mapping.
-   Do not fabricate claims such as "₹500 feeds a family" or "₹1,000
    educates a child."
-   Do not imply that the meter represents a live campaign total unless
    it is connected to a verified, updated data source.
-   If no verified impact mapping or campaign target exists, use the
    meter only as a contribution amount selector and label it clearly.
-   Do not collect card, bank or payment credentials directly in the
    website form.

Suggested initial UI states (amount values are examples for design
review, not approved donation prices):

-   Suggested amount options: to be confirmed by DWA.
-   Custom amount: visitor enters amount.
-   Selected amount: dynamically displayed.
-   Optional campaign progress: disabled until a verified target,
    received amount, reporting period and update owner are supplied.

# 3. Design system --- source of truth

The uploaded DWA Website UI/UX Design Guide is the visual source of
truth. Preserve the approved colours and design principles.

## 3.1 Design vision

The website must feel:

-   Editorial.
-   Spacious.
-   Human-centred.
-   Documentary.
-   Institutional.
-   Calm and credible.
-   Original to DWA.

Use Open Society Foundations as inspiration for design principles only:
confident typography, strong use of space, purposeful photography, clear
navigation and restrained visual effects. Do not copy its branding,
text, images, code or exact page compositions.

## 3.2 Approved DWA colours

Preserve these three approved brand colours exactly.

  -----------------------------------------------------------------------
  Role                    Hex                     Use
  ----------------------- ----------------------- -----------------------
  Primary green           `#2CC980`               Primary calls to
                                                  action, selected states
                                                  and key highlights

  Secondary blue          `#5974CF`               Links, secondary
                                                  actions and navigation
                                                  accents

  Yellow accent           `#F5C21B`               Small accent details,
                                                  markers and restrained
                                                  highlights
  -----------------------------------------------------------------------

Supporting neutrals:

  Role                  Hex         Use
  --------------------- ----------- ---------------------------------
  Main background       `#FFFFFF`   Main page surface
  Warm background       `#FAFAF7`   Alternate editorial sections
  Main text             `#202522`   Body text and headings
  Secondary text        `#5D655F`   Supporting copy and metadata
  Soft divider          `#E7EAE7`   Hairlines and subtle separators
  Placeholder surface   `#F0F2EF`   Image and content placeholders

Colour rules: - Green is the most important action colour. - Blue is for
links and secondary interactive emphasis. - Yellow is used sparingly. -
Do not use all three colours at equal intensity in every section. - Keep
reading surfaces white or warm neutral. - Test contrast; do not change
approved brand hex values to solve contrast problems. - Never rely on
colour alone to communicate meaning.

## 3.3 Typography

  -----------------------------------------------------------------------
  Use                                 Typeface direction
  ----------------------------------- -----------------------------------
  Editorial headings                  Source Serif 4, Georgia or system
                                      serif fallback

  Body and interface                  Inter or system sans-serif fallback
  -----------------------------------------------------------------------

Use locally hosted fonts where possible, or reliable system fallbacks.
Avoid loading unnecessary font families and weights.

Suggested fluid type scale:

  Element                   Desktop      Mobile
  --------------------- ----------- -----------
  Hero headline           56--76 px   38--48 px
  Page title              48--64 px   34--42 px
  Section heading         36--48 px   28--36 px
  Feature heading         28--36 px   24--30 px
  Body copy               17--19 px   16--18 px
  Navigation              14--16 px   16--18 px
  Captions / metadata     12--14 px   12--14 px

Typography rules: - Use sentence case. - Keep body line length around
55--75 characters where practical. - Body line-height should generally
be around 1.5--1.7. - Avoid long paragraphs in hero sections. - Preserve
logical heading order.

## 3.4 Grid and spacing

-   Maximum desktop content width: approximately 1200--1320 px.
-   Main reading width: approximately 620--760 px.
-   Desktop side gutters: approximately 48--72 px.
-   Tablet gutters: approximately 28--40 px.
-   Mobile gutters: approximately 20--24 px.
-   Use a 12-column desktop grid or a simpler equivalent.
-   Use a single-column mobile reading flow.
-   No horizontal page scrolling.

Spacing scale:

`4, 8, 12, 16, 24, 32, 48, 64, 80, 96, 120 px`

Use generous section separation without mechanically applying identical
padding to every section.

## 3.5 Editorial layout

-   Alternate text-led and image-led sections.
-   Use asymmetrical layouts where they improve storytelling.
-   Let selected documentary photographs extend wider than text columns.
-   Use captions and metadata quietly.
-   Prefer open editorial rows for major programme and project features.
-   Avoid a generic SaaS dashboard appearance.
-   Avoid filling every section with cards, icons, badges or boxes.
-   Use subtle dividers and generous whitespace.

## 3.6 Photography and image placeholders

**During the first design phase, create image holders only. Do not
select final images.**

-   Use neutral surface `#F0F2EF`.
-   Use a subtle or dashed border.
-   Label development placeholders clearly,
    e.g. `FIELD PHOTOGRAPH PLACEHOLDER`.
-   No stock photographs, fictional beneficiary photographs or
    AI-generated people.
-   DWA will select photographs from its own gallery after reviewing the
    layout.
-   Do not infer identity, project context, consent or impact from a
    filename or image alone.
-   Do not crop final photographs until the subject and focal point are
    reviewed.

Suggested ratios:

  Image role                 Ratio
  -------------------------- --------------------------------
  Homepage hero              4:5 or 5:4
  Wide documentary feature   16:9 or 2:1
  Programme feature          4:3
  Project feature            3:2
  Story feature              4:5 or 3:2
  Publication cover          3:4
  Gallery                    Flexible; preserve focal point

## 3.7 Header and navigation

Desktop: - DWA logo/name on the left. - Five primary navigation items on
the right or balanced central/right. - One restrained primary action, if
approved. - Compact header; sticky behaviour is optional. - No crowded
utility links.

Mobile: - DWA identity and accessible menu control. - Keyboard and
screen-reader operation. - Comfortable touch targets. - Return focus to
the menu control when closed. - No hover-only navigation.

## 3.8 Components and interactions

Buttons: - Primary green `#2CC980`, with contrast-tested text. -
Secondary blue `#5974CF` or outlined treatment. - Yellow `#F5C21B` for
restrained emphasis, not automatically for text buttons. - Include
hover, focus, active and disabled states.

Links: - Recognisable without relying on colour alone. - Underline or
use a consistent inline-link cue. - Descriptive labels.

Tabs and in-page menus: - Use semantic buttons or links with accessible
selected/current states. - Keyboard navigable. - On mobile, use a
compact dropdown, scrollable tab strip or accordion. - Anchor navigation
must work without JavaScript where practical. - Do not create a second
hidden set of top-level pages.

Forms: - Visible labels. - Clear required-field indication. -
Client-side and server-side validation. - Helpful error and success
messages. - Privacy explanation. - Spam protection for backend-connected
forms.

Motion: - Subtle and purposeful only. - Respect
`prefers-reduced-motion`. - No distracting parallax or scroll effects. -
All content must remain available without animation.

page.

available, use narrative copy rather than invented numbers. - Do not
invent a slogan; use only DWA-approved wording. - Keep all other primary

## 5.5 Data ownership rules

-   Salesforce is the primary donor record system.
-   monday CRM must have a separate, documented operational purpose.
-   monday Work Management is for tasks and project delivery, not a
    second donor database.
-   D1 is for limited website records only, not a shadow CRM.
-   Do not duplicate personal data across platforms without a documented
    business need.
-   Document the owner and retention rule for every form field.
-   Collect only the information needed for the stated purpose.

## 5.6 Form and integration architecture

Suggested secure flow:

`Website form → Cloudflare Worker → server-side validation → spam protection → approved CRM destination`

-   Keep CRM credentials in Cloudflare Worker secrets/environment
    variables.
-   Never put private API keys in browser JavaScript.
-   Use least-privilege CRM permissions.
-   Validate and sanitize all submitted data.
-   Add rate limiting and abuse protection.
-   Handle API failures safely.
-   Do not claim an enquiry or donation has succeeded until the
    receiving service confirms it.
-   Do not collect card details directly on DWA's website.

CRM integrations are later-phase work. Do not integrate Salesforce,
monday.com, payments, analytics, email marketing or an AI chatbot during
the visual design phase.

# 6. Image optimization and media handling

## 6.1 Optimization workflow

-   Preserve original master photographs separately.
-   Create web-ready AVIF or WebP variants where supported.
-   Provide appropriate fallbacks.
-   Generate multiple widths for responsive screens.
-   Use `srcset` and `sizes`.
-   Set image width and height to reduce layout shifts.
-   Lazy-load below-the-fold images.
-   Preload only the key hero image when appropriate.
-   Use descriptive filenames, captions and alt text.
-   Keep image payloads proportionate to their rendered dimensions.
-   Store approved public assets in R2.
-   Do not expose private or unapproved images through public URLs.

## 6.2 Image approval

Before publishing an image, DWA must confirm: - Correct
project/activity. - Location and date, if known. - Consent and
publication permission where required. - Image rights and photographer
details. - Respectful representation. - Factually correct caption. -
Accurate alt text. - Safe crop and focal point.

Children's photographs and identifiable beneficiary images require
particular care and appropriate authorization.

# 7. Accessibility, performance, SEO and security

## Accessibility

-   Semantic HTML landmarks and logical heading order.
-   Keyboard-operable menus, tabs and forms.
-   Visible focus states.
-   Sufficient colour contrast.
-   Programmatic form labels and useful errors.
-   Meaningful alt text for informative images; empty alt for decorative
    images.
-   No reliance on colour alone.
-   No hover-only content.
-   Respect reduced-motion preferences.
-   Test browser zoom and small screens.

## Performance

-   Static HTML wherever possible.
-   Production-minified Tailwind CSS.
-   Small Vanilla JavaScript bundle.
-   Defer non-critical scripts.
-   Avoid large frameworks and unnecessary third-party scripts.
-   Use responsive optimized images.
-   Use Cloudflare caching appropriately.
-   Avoid autoplay video and oversized animations.
-   Monitor Core Web Vitals after launch.

## SEO

-   Unique page title and description for each of the five pages.
-   Semantic headings.
-   Canonical URLs where appropriate.
-   XML sitemap containing only the five primary pages and any approved
    public URL structure.
-   Robots configuration.
-   Open Graph metadata and social sharing images.
-   Descriptive internal links.
-   Organization structured data only with verified details.
-   No fabricated ratings, reviews or impact data.

## Security and privacy

-   HTTPS.
-   Secrets stored in Cloudflare Worker secrets.
-   Server-side form validation and sanitization.
-   Rate limiting and spam protection.
-   Least-privilege CRM/API permissions.
-   Role-based access to GitHub, Cloudflare, Salesforce and monday.com.
-   Document data collection purpose, retention and deletion.
-   Do not put personal data in URLs or analytics events.
-   Do not expose private documents or beneficiary information.
-   Define incident response and privacy request ownership.

# 14. Google Antigravity --- master implementation instructions

The following instructions are intended to guide the Antigravity coding
agent.

## 14.1 Read and obey project specification

Treat this document as the master source of truth for scope, sitemap,
design, stack and implementation sequence.

Treat the uploaded `DWA Website UI/UX Design Guide` as the source of
truth for visual design details.

Use the approved DWA content master as the source for organizational
facts. Do not invent facts, metrics, beneficiary stories, credentials,
addresses, donor relationships, donation links or contact information.

If a fact is missing or conflicting, mark it for DWA confirmation. Do
not silently guess.

## 14.2 Scope enforcement

-   There are exactly five primary pages: Home, About, Programs,
    Accountability and Donate.
-   All secondary content must be in-page sections, tabular menus,
    anchor navigation, accordions or structured content within those
    five pages.
-   Do not create extra top-level pages.
-   Phase 1 is Home page only.
-   Do not implement the other four pages until DWA's written Home page
    approval.
-   Do not integrate CRM, payment processing, analytics, email marketing
    or AI during the visual design phase.
-   Do not replace the selected stack with a front-end framework.

## 14.3 Design enforcement

-   Use DWA green `#2CC980`, blue `#5974CF` and yellow `#F5C21B`
    exactly.
-   Use the approved neutral palette.
-   Use an editorial serif for headings and a clean sans-serif for
    body/interface.
-   Create generous whitespace and clear hierarchy.
-   Avoid generic SaaS dashboards, excessive cards, excessive icons and
    decorative badges.
-   Use neutral image holders only during layout review.
-   Never use stock or AI-generated beneficiary images.
-   Make desktop, tablet and mobile behaviour intentional.
-   Build accessible tabular in-page menus.
-   Respect reduced motion and keyboard operation.

## 14.4 Development workflow

1.  Inspect the repository before changing files.
2.  Report the proposed file changes before major implementation.
3.  Establish the Tailwind build and reusable design tokens.
4.  Implement only the currently approved phase.
5.  Keep code modular and readable.
6.  Use semantic HTML5.
7.  Keep Vanilla JavaScript minimal.
8.  Do not add dependencies without a clear need.
9.  Do not commit secrets.
10. Test build, responsive behaviour, accessibility basics and links.
11. Deploy previews for DWA review.
12. Wait for approval at the defined gate before proceeding.

## 14.5 Phase 1 execution brief for Antigravity

**Build only `index.html` and the minimum shared CSS/JavaScript/assets
required for the Home page.**

labels. - Editorial hero with large image placeholder. - Short DWA
